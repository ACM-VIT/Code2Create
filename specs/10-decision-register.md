# Decision register

This register separates source requirements, implementation choices, and unresolved event policy.

## 1. Confirmed product direction

| ID | Decision |
| --- | --- |
| C-001 | Code2Create 7.0 is a 48-hour event expected to place roughly 900–1,000 people in the venue. |
| C-002 | Participants use a web portal, reviewers use a dedicated mobile application, and staff use a web operations dashboard. |
| C-003 | Participant entry asks VIT Student or External Participant before Google authentication. |
| C-004 | A VIT student must authenticate with the VIT student Google Workspace account. |
| C-005 | Supreme, Board, SC, JC, and External Judge are organizational labels. The labels only suggest default permission bundles. A role change changes no grant. Every protected read or write uses an atomic person-specific permission grant with exact scope and validity. Any event-linked person may receive any permission regardless of role. An explicitly invited account may have no role. Users cannot select their own role label. |
| C-006 | Reviewer UI uses large controls, little text, and one current task. |
| C-007 | Panels are planned before the round from reviewer expertise and rubric coverage. |
| C-008 | Every required panel reviewer scans the review-presence team QR before a normal review starts. |
| C-009 | A person with the separately granted `review.presence.waive` permission for that review can handle an exceptional missing-presence case; fresh authentication, reason, and audit are required. |
| C-010 | Reviewers clock in; an absent reviewer triggers a substitute workflow. |
| C-011 | Staff capture team hall locations before the review window and freeze them before routing. A panel has no place of its own; it walks to the team, so where the team is sitting is where the review happens. |
| C-012 | Participants can only observe their queue and review state. There is no participant readiness declaration or round-entry command. Staff with `queue.manage` for the exact panel place an eligible team directly into that queue. |
| C-013 | Reviews have a time cap and an explicit extension path. |
| C-014 | Reviewers score independently on criteria assigned from their expertise. |
| C-015 | Reviewer seniority does not multiply score weight. |
| C-016 | No AI model generates, changes, normalizes, or recommends judging scores. |
| C-017 | The working rubric uses seven weighted criteria scored 0–4. |
| C-018 | Later reviews receive previous findings, commitments, and progress evidence. |
| C-019 | The working round model is two ordinary reviews followed by a final round. |
| C-020 | Project onboarding begins with **Hello.** and **What is your project about?** The interface shows one text box or prompt at a time. It does not require a PPT or expose a traditional form. |
| C-021 | Every hack project is fresh. Project-specific implementation and design begin at the official event baseline. Teams disclose material general-purpose starting resources and any allowed pre-start setup. There is no continuation category. |
| C-022 | GitHub and Figma resources, live progress facts, and checkpoints are team-scoped. A team can submit several classified repositories. Assigned reviewers inspect the frozen repository set and design, not a member-owned metadata link. |
| C-023 | The application uses normal internet/HTTP connectivity. Bluetooth/P2P is not committed. |
| C-024 | Synesthesia accepts participant requests and votes while staff retain playback control. |
| C-025 | Five core tracks are planned with room for additional sponsor tracks. Track definitions are configurable, and mandatory problem statements were not adopted. |
| C-026 | The guided project intake supports pre-event shortlisting so the organizers can admit fewer teams when venue/review capacity requires it. |
| C-027 | Every active panel reviewer needs a working phone with the reviewer app; otherwise operations supplies a spare or replaces the reviewer. |
| C-028 | An OpenAI layer sits behind the minimal intake to interpret the team's natural-language answer and make the sequence adaptive. |
| C-029 | Event phases and track-dependent guidance require versioned event configuration, not client-side hard-coding. The schedule assigns each phase. |
| C-030 | After the opening description, intake asks one or two short, relevant questions that are mostly easy to answer. A common-idea match may prompt supportive differentiation or follow-through. It never causes an automatic rejection or discouraging novelty verdict. The system validates and versions the questions. The questions do not come from a fixed questionnaire. |
| C-031 | Every expected participant confirms presence individually for each configured hacking session, even when they remained inside the venue between sessions. |
| C-032 | VIT students present the printed barcode on their existing VIT ID to a provisioned staff phone camera. External participants and VIT fallbacks use QR. Every method reaches the same realtime backend state. |
| C-033 | Temporary exits and returns may happen repeatedly during a session and must update current participant presence accurately. |
| C-034 | Attendance sessions and their enforcement are configurable. The scan ledger records facts without hard-coding one global attendance percentage or automatic punishment. |
| C-035 | After Google authentication, every participant completes a class-aware basic profile including name, policy-permitted contact, college/university/institution, and year of study or current role. |
| C-036 | Team creation/joining is available before and throughout intake through a live team area with invite link/code, one explicit lead, and an accepted lead-transfer flow. |
| C-037 | Saving the initial idea immediately opens the complete track list. AI may highlight one track with a short reason. The team may choose any published track and may change it before final submission. The system does not penalize the team for choosing differently. |
| C-038 | The final application screen shows the full team, lead, chosen core track, optional sponsor-track selections, and project summary. The screen explicitly warns that submission locks team membership and the displayed track set. Only an explicit confirmation can perform that lock and submission. |
| C-039 | Admissions must publish a transparent year-adjusted rubric. The rubric has lighter first-year expectations. Later bands have progressively stronger expectations for clarity, feasibility, technical detail, and differentiation. A separate AI analysis returns a structured advisory recommendation. Authorized humans retain final Accept/Waitlist/Decline/Needs information authority. |
| C-040 | Admission recommendation and hackathon judging are separate contexts. AI never writes or recommends judging scores. Choosing against the AI track recommendation is not an admission signal. |
| C-041 | An accepted team receives a focused portal state. The state contains the venue and date, next steps, and the locked team and project summary. Discord is the primary community and support route. The team also receives an official notification route that does not require an open portal. |
| C-042 | Participant onboarding remains low-text, simple, and polished. It uses a restrained cherry-blossom visual direction. It does not become a dashboard, chat transcript, or deck workflow. |
| C-043 | Roving floor staff map teams by scanning a short-lived QR displayed on that team's dashboard and touching where the team is sitting on the drawn zone rectangle. The hall's tables are moved by participants and carry no numbers, so no location is a claim on a numbered seat. The event does not place QR stickers on tables, and participants cannot assign their own location. |
| C-044 | Operations keeps a restricted printable emergency pack. The pack contains the current accepted roster, presence and hall snapshot, stations, active sessions, panels, and uniquely numbered recovery sheets. Printing the pack does not approve paper mode. Used originals still follow the two-person incident reconciliation flow. |
| C-045 | Every participant and approved roster claimant has a simple self-service support route. An invitation-only grantless account receives this route only through an explicit grant. Support ownership and linked context are routing aids only. They do not grant authority. They do not change attendance, queue, team, admission, review, score, integration, or access state. |
| C-046 | While a team writes its initial idea, the portal shows a small live novelty signal against a reviewed corpus of past projects. The signal may identify the closest broad theme and ask one supportive reflection question. It never blocks submission or becomes application evidence. It never affects admission or judging and never penalizes a familiar idea. |
| C-047 | One published participant policy controls class-aware profile fields, team-size bounds, and mixed-class eligibility. It also controls profile and project-text notices, the privacy link, the fixed fresh-project acknowledgment, and the final lock warning. Each participant accepts an exact immutable version on the event membership before saving a profile, creating or joining a team, or submitting the project. Team formation does not wait for profile completion. Final submission still requires every active member's complete class-aware profile. A later publication changes no saved profile or submitted project. |

## 6. Change procedure

When an open item is decided:

1. Add the approved value, date, owner, and source.
2. Mark each superseded row.
3. Update the affected workflow and event configuration.
4. Update the automated tests and rehearsal script.
5. Tell participants or reviewers before the relevant policy freeze.
